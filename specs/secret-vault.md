# Bóveda: end-to-end encrypted secrets unlocked with a passkey (WebAuthn PRF)

**Status:** Implemented on branch `secret-vault` (branched from `car-link-phase0`, so migration numbering continues at 0046); **not applied**. The owner reviews the migration, runs `npx supabase db push` and `npm run gen:types`, merges `car-link-phase0` first and then this branch, and deploys (see "Owner steps").

**2026-11-27 (owner decision):** the QR scan («Escanear el QR del auto») was removed, with `QrScanner`, `qrDecode` and the `jsqr` dependency: the car's Dashcam no longer shows a QR with the words. The words now arrive in one of two ways: the car sends them (`vault-onboarding.md` Phase C) or the owner types the 24 words shown on the car. Items saved with source `qr` keep opening. The text below describes the page as it is now.

## Context

Two secrets protect the owner's car data and today live only on paper or in the owner's head:

1. **The dashcam's 24-word recovery code** (`vigo-hack/dashcam`, `RecoveryCode` / `WordList`): the 32-byte P-256 private scalar of the clip key plus an 8-bit checksum, 24 words of 11 bits from a self-generated list of 2048 words. Without it, recorded clips cannot be opened after a reset or reinstall (`dashcam/DECISIONS.md`, round 2 "Key recovery").
2. **The settings-backup passphrase** (`vigo-hack/settings_backup/sb_crypto.ps1`): encrypts the secret part of a settings bundle (`VIGOSB1` container, PBKDF2-HMAC-SHA256 600 000 iterations, AES-256-CBC + HMAC-SHA256). Typed at run time, never stored, at least 8 characters.

**Owner decision (2026-11-20):** keep both in the owner's WikiVigo account, **end-to-end encrypted with a key derived from a passkey on the owner's phone (WebAuthn PRF extension)**. WikiVigo/Supabase must only ever hold ciphertext. There is **no passphrase to remember and no password fallback**: a browser without PRF gets a clear Spanish message instead.

This fits `vigo-hack/wikivigo/PLAN.md` section 1.4 ("Settings backups are end-to-end encrypted on the car (WikiVigo stores ciphertext only)") and is the first piece of its phase 3 (C1/C2): the passphrase kept here is the one a later cloud copy of the settings bundle would use.

## Requirements

### R1. Crypto envelope (browser, WebCrypto only)

All cryptography runs in the browser through `crypto.subtle`; no crypto library is added.

- **Data key (DK)**: one random 256-bit AES-GCM key per user, generated by WebCrypto (`crypto.subtle.generateKey`, the browser's CSPRNG) when the first passkey is enrolled. It never leaves the browser unwrapped and is never stored unwrapped anywhere (not in `localStorage`, not in IndexedDB, not in React state after the operation that needed it).
- **Items**: each secret is encrypted with the DK, **AES-256-GCM**, a fresh random 96-bit IV per write, 128-bit tag, and **AAD** = UTF-8 of `"vigo-vault/item/v1" ‖ 0x00 ‖ user_id ‖ 0x00 ‖ kind ‖ 0x00 ‖ version`. Moving a ciphertext to another user, another kind or another format version makes decryption fail.
- **Plaintext format** (inside the ciphertext only): JSON `{"v":1,"value":"…","source":"typed|car|generated|qr|paste","savedAt":"<ISO time>"}` (`qr` and `paste` are no longer written but are still accepted when reading), right-padded with spaces to **exactly 512 bytes** so every ciphertext has the same length (the server learns nothing from the length of a passphrase). A value whose JSON exceeds 512 bytes is refused before encryption. `savedAt` is shown after a reveal, so a server-side rollback to an older ciphertext is visible as an older date.
- **Key-encryption key (KEK), one per passkey**: the passkey's PRF output (exactly 32 bytes, refused otherwise: HKDF would accept an empty or short input and derive a predictable key; WebAuthn `prf` extension, CTAP2 `hmac-secret` underneath) evaluated on that passkey's random 32-byte `prf_salt` → **HKDF-SHA-256** (salt empty, info = `"vigo-vault/kek/v1" ‖ 0x00 ‖ user_id ‖ 0x00 ‖ credential_id`) → a non-extractable AES-256-GCM key usable only for `wrapKey`/`unwrapKey`.
- **Wrapped DK, one per passkey**: `wrapKey('raw', DK, KEK, AES-GCM)` with a fresh 96-bit IV and AAD = `"vigo-vault/dk/v1" ‖ 0x00 ‖ user_id ‖ 0x00 ‖ credential_id`; stored as base64 of `IV ‖ ciphertext ‖ tag` (12 + 32 + 16 = 60 bytes). AES-GCM rather than AES-KW so the wrap is bound to the user and the credential (AAD).
- **Several passkeys**: each enrolled passkey stores its own wrap of the **same** DK. Adding a passkey needs one that already works (unwrap the DK as an extractable key for the duration of that flow only, wrap it for the new passkey). Removing a passkey deletes its row (its wrap); the other wraps keep working.
- **No caching**: every operation that needs the DK (save, reveal, add a passkey) runs its own WebAuthn assertion with user verification. The DK is unwrapped non-extractable (except in the add-a-passkey flow), used, and dropped.

### R2. WebAuthn (client side only)

- **Registration**: `navigator.credentials.create` with `rp = { id: <current host>, name: 'WikiVigo' }`, `user.id` = the 16 bytes of the Supabase user UUID (opaque, no PII), `user.name` = the account e-mail (shown only in the owner's passkey manager), `displayName` = `"<e-mail> (Bóveda WikiVigo)"`, `pubKeyCredParams` ES256/EdDSA/RS256, `authenticatorSelection: { residentKey: 'preferred', userVerification: 'required' }`, `attestation: 'none'`, `excludeCredentials` = the user's enrolled credentials (no second vault key on the same authenticator), random 32-byte challenge, `extensions: { prf: { eval: { first: prf_salt } } }`.
- **PRF detection**: before offering the button, `PublicKeyCredential` must exist; when the browser exposes `PublicKeyCredential.getClientCapabilities()`, `'extension:prf' === false` marks the browser as unsupported up front. After `create`, `getClientExtensionResults().prf.enabled !== true` means the authenticator cannot do PRF: the credential is not stored (and, when the browser offers `PublicKeyCredential.signalUnknownCredential`, the authenticator is told to forget it), and the page shows the unsupported message. When `create` already returned `prf.results.first` it is used; otherwise one follow-up `get` evaluates the PRF (some authenticators only evaluate on assertions).
- **Unlock**: `navigator.credentials.get` with `allowCredentials` = the user's enrolled credentials, `userVerification: 'required'`, random challenge, and the PRF salts: `prf.eval` when there is one credential, `prf.evalByCredential` (base64url credential id → salt) when there are several. The returned `rawId` selects the row; a missing `prf.results.first`, an output that is not 32 bytes, or an assertion whose authenticator data lacks the UV flag is an error.
- **Adding a device**: the new device first unlocks with an existing passkey (synced to it, or another phone through the browser's cross-device QR), so a failed unlock creates nothing; then it creates its own passkey (`excludeCredentials` refuses a second vault passkey on the same authenticator) and stores its wrap after proving it unwraps.
- **RP ID = the page's host**: `fedeazzato.github.io` in production (`localhost` in `npm run dev`). Implications, all accepted and documented in the threat model:
  - `github.io` is on the Public Suffix List, so the RP ID cannot be wider than `fedeazzato.github.io`, and **every GitHub Pages site of that account shares the origin `https://fedeazzato.github.io` and the RP ID**: any page published there could ask for these passkeys (the user still sees the OS prompt and must verify).
  - Passkeys are bound to that RP ID: if WikiVigo moves to its own domain, every passkey must be enrolled again **before** the old site goes away (unwrap on the old origin, re-wrap on the new one), or the vault content is lost.
  - `HashRouter` is irrelevant to WebAuthn (it binds to the origin, not the path or hash) and **no server callback exists**: registration and assertion are fully client-side.
- **The server never verifies attestations or assertions, on purpose.** Supabase authentication stays email OTP; the passkey is used only as a *key-derivation device* (its PRF output), never as a login. Verifying assertions on the server would add nothing: the server holds only ciphertext, and possession of the DK requires the authenticator's PRF output, which only the authenticator can produce (after user verification). A forged or replayed assertion yields no PRF output. The server's only job is a **blob store with RLS**: each row is readable and writable by its owner's session only. The challenge is therefore random and client-generated, and the signature is ignored.
- **User verification is required everywhere** (`'required'` on create and get). For CTAP2 `hmac-secret` authenticators the PRF secret used with UV differs from the one without UV, so a PRF evaluation without UV yields a different (useless) KEK.

### R3. Migration `0046_secret_vault.sql`

Tables (RLS enabled; `anon` has no privilege at all; not referenced by any view or function readable by others):

- **`vault_keys`**: `user_id uuid not null default auth.uid() → auth.users on delete cascade`, `credential_id text` (base64url `^[A-Za-z0-9_-]+$`, 16..1400 chars checked with `char_length`: Postgres regex repetition counts stop at 255), `prf_salt text` (base64 of exactly 32 bytes), `wrapped_dk text` (base64 of exactly 60 bytes), `label text` (1..40 chars, no control characters), `created_at timestamptz default now()`. Primary key `(user_id, credential_id)`. At most **10 passkeys per user** (trigger).
- **`vault_items`**: `user_id uuid not null default auth.uid() → auth.users on delete cascade`, `kind text check (kind in ('dashcam_recovery', 'settings_backup_passphrase'))`, `version smallint not null default 1 check (version = 1)` (envelope format version, part of the AAD), `iv text` (base64 of exactly 12 bytes), `ciphertext text` (base64, 24..2800 chars, about 2 KB raw at most; the client always writes 528 bytes), `updated_at timestamptz default now()` (set by a trigger on every update). Primary key `(user_id, kind)` (= unique per user and kind).
- **`vault_write_log`**: one row per insert/update on either table (user_id, at). RLS on, no policies, no grants: only the SECURITY DEFINER trigger touches it.

Privileges and RLS (own rows only):

| Table | `anon` | `authenticated` grants | Policies (`to authenticated`) |
|---|---|---|---|
| `vault_keys` | none | `select`; `insert (credential_id, prf_salt, wrapped_dk, label)`; `delete` | select / insert / delete: `user_id = auth.uid()` |
| `vault_items` | none | `select`; `insert (kind, version, iv, ciphertext)`; `update (version, iv, ciphertext)`; `delete` | select / insert / update / delete: `user_id = auth.uid()` (update also `with check`) |
| `vault_write_log` | none | none | none |

- `user_id` is never client-writable (no column grant): it always comes from `default auth.uid()`, and the policies' `with check (user_id = auth.uid())` reject everything else. Vehicle members, moderators and anon see nothing: no policy mentions vehicles or moderators.
- No update on `vault_keys` (a passkey is removed and enrolled again); no update of `kind` on `vault_items`.
- **Daily write limit**: the trigger `enforce_vault_write_limit()` (SECURITY DEFINER, `search_path = public`) logs every insert/update and raises `Límite diario de 20 cambios en la bóveda alcanzado. Probá de nuevo mañana.` at the 21st in a rolling 24 h window per user (20 per day, like `enforce_daily_insert_limit`, 0009). **Deletes are never limited** (removing a lost passkey must always work; deletes cannot flood because the row count is bounded). Log rows older than 2 days are purged opportunistically.
- **Passkey cap**: `enforce_vault_key_cap()` raises `Ya tenés 10 llaves en la bóveda. Quitá una antes de agregar otra.`.
- Banned users keep access to their own vault (it is private data, not community content; locking someone out of their own secrets would only cause loss).
- Both trigger functions have `execute` revoked from `public`, `anon`, `authenticated` and `service_role` (trigger functions run regardless; see 0015 section 5 on Supabase default privileges).

### R4. Recovery-code parity with the dashcam

`src/lib/vault/recoveryCode.ts` ports `RecoveryCode.decode` exactly:

- Word list: the same 2048 words (`src/lib/vault/recoveryWords.ts`, generated from the dashcam's `WordList`), pinned by the dashcam's golden SHA-256 of the words joined by `\n` (with a final `\n`): `5bf1619c6549db2fc3d57767fe2730f5c68d9f881f3de3ce4bcfeedb856cac3e`.
- Parsing: lower case, any run of non-`[a-z]` separates words (spaces, commas, newlines, numbering such as `7.`), exactly 24 words, each in the list, 11 bits each (most significant first) → 33 bytes; the last byte must equal the first byte of `SHA-256("vigo-dashcam-recovery-v1" ‖ scalar)`.
- Errors (Spanish, never echoing the words): wrong count, unknown word at position *n*, bad checksum.
- **Prefixed form** (`vigovault:dashcam:1:` + the 24 lowercase words joined by single spaces, at most 163 bytes): what the car showed as a QR until the QR was removed (2026-11). The parser still accepts it as typed or pasted text; other versions (`vigovault:dashcam:2:`) are refused.
- Shared test vectors (made with the Java `RecoveryCode.encodeToString`; public data, no real key): the scalars 0, 1, all-ones and SHA-256(`vigo-vault-test-vector-N`), N = 1..5. The same eight vectors are pinned in the dashcam's Java tests.
- What is stored is the canonical form (24 lowercase words, single spaces).

### R5. Settings-backup passphrase

- **Generate**: 10 words from the same 2048-word list (`crypto.getRandomValues`, 11 bits per word by masking a 16-bit value: no modulo bias), joined by `-`: about 50 lowercase ASCII characters, **110 bits** of entropy, easy to type on the laptop at `backup_car.ps1`'s prompt.
- **Keep an existing one**: 8..200 characters (`sb_crypto.ps1` requires at least 8), no control characters.

### R6. Web UI: Mi Vigo → "Bóveda" (`/mi-vigo/boveda`)

- Mi Vigo (signed in) gets a "Bóveda" card under the car devices: one sentence and a "Abrir la bóveda" link. The page is a lazy route inside `RequireAuth`.
- **Unsupported browser**: `Alert` "Este navegador no puede usar llaves de acceso con cifrado (PRF)…" naming what works (Chrome on Android, Safari on iPhone with iOS 18 or later, a FIDO2 security key in Chrome/Edge/Firefox), and the actions stay disabled. No password fallback.
- **Llaves de acceso** card: list (label, "Agregada el {fecha}", "Quitar"), "Activar con huella o rostro" when there is none, "Agregar otro dispositivo" afterwards, with an optional "Nombre de este dispositivo" field (default from the platform: "Teléfono Android", "iPhone", …). Removing asks for confirmation; removing the **last** passkey says plainly that the saved secrets become unreadable and deletes them too. If items exist but no passkey (all removed elsewhere), the page says the content cannot be opened any more and offers "Borrar lo guardado" before a new enrolment.
- **"Frase de recuperación de la dashcam"** card: "Guardada el {fecha}" / "Todavía no guardaste la frase" + what to do ("Escribir las 24 palabras"; with the inbox enabled, also the "Recibir la frase desde el auto" card); the description names where the car shows them ("Dashcam › Ajustes › Frase de recuperación (te pide el PIN) › «Ver las palabras»"); actions "Escribir las 24 palabras" (textarea accepting the 24 words in any layout, validated live with the parity rules; `RecoveryWordsForm`, shared with the post-pairing checklist), "Ver" (passkey confirmation, then the 24 words numbered in 4 columns of 6, like the car), "Copiar" (with a warning) and "Borrar". No camera is used.
- **"Clave de respaldo de ajustes"** card: "Generar una clave fuerte" (shows the generated value once with copy, then "Guardar en la bóveda"), "Guardar una que ya tengo", "Ver", "Copiar", "Borrar". A hint explains where it is used (`backup_car.ps1 -Backup` asks for it).
- **Plaintext hygiene**: never logged, never sent (the tests assert no plaintext in any Supabase payload); inputs have `autoComplete="off"`, `spellCheck={false}`, `autoCorrect="off"`, `autoCapitalize="none"` (Chrome's enhanced spell check would send the text to Google); a revealed value is cleared after 2 minutes, when the page becomes hidden (`visibilitychange`), and on unmount; the words and passphrase fields are cleared after saving and on unmount. Copying shows "Lo copiado queda en el portapapeles: otras apps pueden leerlo. Pegalo donde lo necesites y después copiá otra cosa." JavaScript strings cannot be zeroed; the page drops every reference instead.

## Threat model

Assets: the 24 words (the dashcam clip private key), the settings-backup passphrase. Not assets: ciphertexts, wrapped DKs, PRF salts, credential ids (all public-safe by construction).

| Threat | Mitigation | Residual risk |
|---|---|---|
| **Database leak, Supabase operator, backups, service-role key** | Only ciphertext, wrapped DKs, salts and credential ids are stored. Decryption needs a PRF output that only the enrolled authenticator produces after user verification. | Metadata: which kinds exist, when they changed, how many passkeys and their labels (labels are user-chosen; keep them generic). |
| **Stolen Supabase session** (copied token, unlocked laptop) | RLS limits it to the owner's rows; reading gives ciphertext only; a new passkey row cannot wrap the real DK without an existing passkey's PRF output. | Deletion (availability) and junk writes (20 per day). The words still exist on the car (Settings after the PIN) and on paper. |
| **Server swaps or rolls back rows** | AAD binds user, kind and version (items) and user and credential (wraps): a swapped row fails to decrypt. `savedAt` inside the ciphertext shows the age after a reveal. | A rollback to an older ciphertext of the same user and kind decrypts (shows its older date). Values rarely change. |
| **Malicious or compromised web code** (WikiVigo bundle via the GitHub account, Actions or an npm dependency; another site on `fedeazzato.github.io`, which shares the origin and the RP ID; the Cloudflare Turnstile script the login page loads into the same document) | Pinned dependencies (lockfile), no runtime CDN for vault code, nothing is unlocked without a tap **and** the OS passkey prompt with user verification, no DK caching. | **The fundamental limit of browser E2E encryption**: code running in the origin when the owner approves a prompt can read what is unlocked. Do not publish untrusted pages under `fedeazzato.github.io`; a dedicated domain later would isolate the origin (passkeys must then be re-enrolled, R2). |
| **Phone stolen or borrowed** | `userVerification: 'required'` on every operation (biometric or the phone's screen lock); the OTP session alone opens nothing. | Someone who knows the phone's PIN and holds the phone can unlock. Remove that passkey from another device (R6). |
| **Synced passkeys** (Google Password Manager, iCloud Keychain) | They are end-to-end encrypted by the provider and need a device screen lock to join the sync; they also mean a lost phone does not lose the vault. | Whoever controls the Google/Apple account **and** a device screen lock in that sync circle can use the passkey. |
| **Shoulder surfing, screenshots, screen recording** | Reveal only on demand, auto-hide after 2 minutes and when the page is hidden. | The web cannot block screenshots (the car app uses FLAG_SECURE; a browser has no equivalent). |
| **Clipboard** | Copy only on an explicit tap, with a warning. | Other apps and keyboards may read the clipboard. |
| **Keyboard / spell check / autofill leaks** | `spellCheck=false`, `autoComplete=off`, `autoCorrect=off`, `autoCapitalize=none` on every secret field. | Third-party keyboard apps may still learn typed words (having the car send them avoids typing). |
| **Downgrade to no-PRF or no-UV** | No password fallback (owner decision); PRF with UV only; an authenticator without PRF is rejected at enrolment. | None. |
| **Rate abuse** | 20 writes per user per day, 10 passkeys, 2 items, fixed size limits. | None material. |
| **Loss of ALL passkeys** | Enrol a second passkey on another device or a security key (R6 nudges after the first one); synced passkeys survive a lost phone. | **If every passkey is lost, the vault cannot be opened by anyone, including the site owner — by design.** The dashcam words then exist only on the car (Settings → Frase de recuperación, after the PIN) and on the paper copy; if the car's key is also gone, unwritten words are lost for good. A settings-backup passphrase generated here and never written down is lost with them, and with it every `secret.vsb` encrypted under it: write it on paper too. |

## Implementation notes

- The migration was executed during development against PGlite 0.3.14 (Postgres 17 in WASM) after all 45 earlier migrations, with Supabase-like roles (`anon`, `authenticated`, `service_role` with BYPASSRLS), Supabase's default privileges and a stub `auth` schema: **88 assertions covering every checklist item passed** (including a vehicle mate, a banned user, the 2-day log purge and the auth-user cascade). The harness lives outside the repo (as for car-link phase 0; no new dev dependency). It found one real issue, fixed before commit: `{16,1400}` in the credential-id regex is invalid in Postgres (repetition counts stop at 255), so every key insert would have failed.
- The vitest fake authenticator (`src/test/fakeAuthenticator.ts`) models CTAP2 `hmac-secret` (HMAC-SHA-256 of the hashed PRF salt per credential). Writing it found a second issue, fixed before commit: a PRF result from another JavaScript realm failed an `instanceof ArrayBuffer` check and became an empty buffer, which HKDF accepted; the code now uses `ArrayBuffer.isView` and refuses any PRF output that is not 32 bytes (in the WebAuthn layer and in `deriveKek`).
- `database.types.ts` is hand-extended until `npm run gen:types` runs against the migrated project.
